## 新流程变更点（相较 v1.0）

1. 轨迹过滤逻辑改为 `run_window`：仅保留本次 `opencode run` 生成报告流程中的 trace，不混入历史会话。
2. 权限基线固定为 `.opencode/opencode.json` 允许 `bash`，避免关键步骤被 auto-reject。
3. 审计报告固定输出“失败工具调用明细”，即使无失败也显示“无”。

## 公式复核（可追溯计算）

审计公式：

```text
Score = (W1 x 结果正确性) + (W2 x SOP依从度) - (W3 x 步骤惩罚)
W1=0.5, W2=0.5, W3=0.2
```

### 1) 结果正确性

```text
结果正确性 = (工具成功率 + 参数准确度) / 2
         = (100.0 + 100.0) / 2
         = 100.0
```

### 2) SOP依从度

```text
SOP依从度 = (关键动作覆盖率 + 顺序一致性 + 禁忌行为评分) / 3
         = (100.0 + 100.0 + 100.0) / 3
         = 100.0
```

### 3) 步骤惩罚

```text
步骤惩罚 = 0.5*步骤惩罚项 + 0.3*Token惩罚项 + 0.2*冗余惩罚项
        = 0.5*40 + 0.3*0.29 + 0.2*0
        = 20.087 ≈ 20.09
```

### 4) 综合得分

```text
Score = 0.5*100.0 + 0.5*100.0 - 0.2*20.09
      = 50 + 50 - 4.018
      = 95.982 ≈ 95.98
```

复核结果：与报告一致。

## 优化建议

### 短期（立即可执行）

   将流程运行与审计固定为单入口：`run_pipeline_and_audit.py`。
2. 继续使用 `run_window` 过滤，确保 trace 只覆盖本次业务流程。
3. 固化执行口令为 `uv run python`，降低环境差异导致的失败重试。

### 中期（1-2 迭代）

1. 提升插件 token 捕获率，尽量从 runtime 事件拿到 `explicit` token。
2. 基于真实历史运行数据重标定 `baseline_steps` 与 `baseline_tokens`。
3. 在 CI 或批处理中增加“效率退化告警阈值”（例如分数下降 >10 分触发告警）。
